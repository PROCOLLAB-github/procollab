# Короткая регистрация в клиентском экземпляре

Существующая `/program-registration/:id` получает дополнительный вариант из API.
При `account_mode: "email_password"` новый участник вводит почту, пароль/повтор и
подтверждает прежние согласия. ФИО и дата рождения скрыты и отсутствуют в payload;
обязательность динамических вопросов анкеты остается. Письмо и подтверждение
используют существующий flow, затем открывается программа без общего онбординга.

`branding: {name, logo_url}` задает имя и логотип формы, входа и заголовка вкладки.
Без логотипа показывается имя клиента. Компоненты, Mont, стили, состояния формы,
ошибки, ссылки, сохранение ответов, подтверждение почты и permissions сохраняются.
Новая страница и новый макет не создаются; квиз не входит в изменения.

Без новых ключей API форма сохраняет полные поля и бренд PROCOLLAB. Отдельно
TokenService сохраняет production cookies для текущего клиентского host;
домен `.procollab.ru` используется на доменах платформы, ключи dev/prod прежние.

## Критерии и проверка

- WL10: скрытые поля профиля отсутствуют в payload, остальные проверки работают.
  Component tests: короткая/полная форма, пароли, согласия, вопросы и переход назад.
- WL11: имя/логотип и заголовки зависят от API, обычная форма сохраняет бренд.
  Component и HTTP adapter tests проверяют в том числе вложенное snake/camel casing.
- WL12: клиентский host получает собственные production cookies, домены платформы
  сохраняют общий domain. TokenService tests включают похожие посторонние домены.

Проверки 10 ноября 2026: 44 целевых Vitest tests (component, HTTP adapter,
TokenService, AuthRequiredGuard и BearerTokenInterceptor), scoped ESLint/Prettier,
`test:solution-contract`, production Angular build. Полный Vitest suite не запускался.
Сборка проходит с предупреждениями Sass, budgets и CommonJS в существующих файлах.

В браузере Chromium production сборка работала с настоящим локальным API и
отдельной PostgreSQL. Проверены desktop 1440×1000 и mobile 390×844, регистрация →
локальное письмо → подтверждение → программа → reload с сохранением сессии.
Дополнительно проверены фокус с клавиатуры, отсутствие горизонтального скролла,
ошибка обязательных данных, переключение входа/восстановления. Консольных JS ошибок
в сценарии не было. Внешние запросы блокировались; адреса API перенаправлялись на
loopback перехватом браузера. Изображение логотипа проверено unit tests, реальные
клиентские assets еще не предоставлены. Детектор ошибочно пометил Angular `[src]`
как отсутствующий `src`; привязка и условие непустого URL подтверждены по source.

## Внедрение

Сначала backend с добавочным контрактом, затем этот frontend. White label на
общем стенде по умолчанию выключен. Схема БД не меняется. Отдельная `pilot`
configuration использует `/backend`, свой WebSocket URL, host-only cookies с
префиксом `pilot_`, отдельный index/noindex и бренд экземпляра из `/instance/`.
Обычные dev/production configurations сохраняют свой контракт.

11 ноября владелец опубликовал изолированный пилот `pilot.procollab.ru` с брендом
«Сознание права», HTTPS, внешним gate и новой БД без данных dev/prod. На пилот
установлен backend из API PR #861 и frontend `6a3d90f1`: исправлено приглашение
участника без ФИО по полной почте только в программе экземпляра. Окно показывает
реальную почту из scoped ответа API; строка команды использует ID. Отсутствующая
дата рождения не превращается в возраст, профиль не заполняется вымышленными
значениями. Обычный поиск по имени сохраняется.

На опубликованном стенде Chromium проверил вход пяти ролей и короткую
desktop/mobile регистрацию двух новых QA-аккаунтов. После подтверждения почты
через обычный API по локальным письмам участники автоматически вступили в
программу, лидер вошел без онбординга и создал проект через UI. После исправления
он нашел участника по почте, отправил приглашение (201), участник принял его
с телефона (200). В команде видны оба аккаунта; чужой аккаунт получает 403 при
попытке принять приглашение.

В пустой демопрограмме через существующие настройки организатора добавлены
явно тестовый кейс и поле файла. Лидер выбрал кейс, загрузил PDF через UI (201,
download побайтно совпал) и сдал проект через подтверждение (200). Organizer
видит сданную работу. После сдачи guard переводит редактор в просмотр; сервер
запрещает изменение команды/полей и повторную сдачу. Проверены mobile 390×844,
отсутствие горизонтального скролла и page errors.

Полный mobile password recovery также пройден: запрос/установка через UI,
возврат к программе, отказ старого пароля и использованной ссылки, вход по новому
паролю. Исходный пароль тестового аккаунта восстановлен через обычный API.
Реальные письма, клиентские материалы/критерии/веса, нагрузка на 100 участников,
клиентский домен и приемка остаются следующими этапами. Квиз не переносится.

## Исправление возврата ко входу, 12 ноября 2026

Обнаружен разрыв маршрутов: корень пилота открывает клиентскую регистрацию,
а выход ведет на общий `/auth/login`. После клиентского входа дополнительно
требуется нажать «Открыть программу». Исправление использует существующую
форму и ее состояния; макет, backend, роли, регистрация и схема БД не меняются.

План: перенаправить общие маршруты входа и запроса восстановления пароля
на соответствующие состояния клиентской формы; после успешного входа
в экземпляре сразу открыть программу. Для обычной платформы сохранить
прежний переход от входа к заполнению анкеты программы.

- WL13: выход, прямой `/auth/login` и вход из защищенной ссылки показывают
  ту же клиентскую форму, что доступна из регистрации.
- WL14: успешный вход в экземпляре сразу открывает программу, включая
  организатора и эксперта без регистрации в качестве участника. Новая
  регистрация в программе при входе не создается.
- WL15: безопасный внутренний `returnUrl` сохраняется; внешний адрес
  игнорируется. Запрос восстановления открывает существующее состояние
  восстановления, а подтверждение почты сохраняет приоритет.
- WL16: при выключенном клиентском режиме маршруты общей авторизации
  и вход на публичной форме программы работают по прежнему контракту.

Проверка: route/component tests, pilot и production builds, браузерный
сценарий вход → программа → выход → повторный вход на пилоте. Публикация
только frontend пилота, без изменения dev/prod и их данных.

Проверки исправления: 48 целевых Vitest tests (routes, public registration,
AuthRequiredGuard, безопасный returnUrl), TypeScript solution contract,
scoped ESLint/Prettier и обе сборки — pilot/production — прошли. Сохраняются
прежние предупреждения Angular/Sass/budgets/CommonJS вне затронутых файлов.

Исходная ошибка воспроизведена на опубликованном пилоте: после выхода
открывается `/auth/login` с общим макетом, домен остается пилотным.
Новая compiled pilot сборка проверена в Chromium с подстановкой только
локальных статических файлов поверх HTTPS и настоящим API пилота. Десять
browser checks прошли: короткая регистрация, вход без лишнего шага, reload,
выход на клиентскую форму, повторный вход, восстановление на mobile 390,
старая ссылка регистрации, защищенная ссылка, вход организатора и отсутствие
JS ошибок. Разрешены только POST входа/выхода собственных QA-сессий;
регистрация, письма, данные программы и критерии не изменялись.

Review WL13–WL16: PASS по tests/build/browser и source trace. Новый макет,
API и permissions не добавлялись. Полная новая регистрация/подтверждение
и установка нового frontend на сервер в этой проверке не выполнялись;
существующая приемка регистрации остается отдельным evidence. На стенде
до установки сохраняется frontend `971e52fb`.
