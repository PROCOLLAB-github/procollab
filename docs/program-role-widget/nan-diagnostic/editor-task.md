# P1: восстановить сохранение очистки файлов проекта в Angular-редакторе

**Отдельная задача редактора, не регрессия #348. Препятствие для дальнейшего релиза редактора:** пользователь удаляет презентацию, файл исчезает, но ссылка проекта не очищается. Даже «сохранить черновик» показывает успех, оставляя ссылку на недоступный файл. Эффект воспроизведён на Angular base `99c8813a66f89560a946eab7d1de73ab2925d0f5` и head `239e3a5eafe653291daf95930ecac9824314f365` при одном backend `3d84c7f4090985e4f42a13654e8fb05856f65cb3`.

## Воспроизведение

1. Только локальные Angular/backend и отдельная тестовая БД. Подготовить лидера, доступный для редактирования черновик проекта 31, связь программы 73, непустую презентацию с принадлежащим лидеру `UserFile` и реальным локальным файлом. Оставить обложку и остальные обязательные поля заполненными.
2. Открыть `/office/projects/31`, нажать «редактировать». Маршрут `/office/projects/31/edit?editingStep=main`. При непустых файловых полях начального NaN нет.
3. Нажать корзину презентации. Штатный `DELETE /files/?link=…` возвращает 204, поле пустое. Единственная попытка записать очистку — `PUT /projects/NaN/`, body `{"presentation_address":"","draft":true}`, 404.
4. Через 10 секунд перечитать проект и файл: проект содержит прежний URL, файл возвращает 404. Уйти через «проекты», ждать 10 секунд, повторно открыть редактор. Поле показывает «Файл успешно загружен» по устаревшему URL.
5. Повторно очистить поле и нажать «сохранить черновик». DELETE уже удалённого файла возвращает 404, существующий обработчик всё равно очищает control. Снова NaN PUT. Явный PUT `/projects/31/` возвращает 200, UI показывает «данные успешно сохранены», но payload не содержит `presentation_address`. Последующий GET всё ещё содержит старый URL.
6. Восстановить исходные данные/файл и повторить на точном base. Результат тот же. Новый виджет не нужен для воспроизведения.

Дополнительный простой сценарий фонового запроса: открыть тот же редактор с изначально пустой презентацией — начальный `patchValue` запускает такой же NaN PUT без действий пользователя. В этом варианте запрос лишний, а изменение обычного непустого названия и кейса успешно сохраняется явной кнопкой.

## Установленная причина

- Root `ProjectFormAutosaveService` читает `projectId` из root `ActivatedRoute.params={}` (`project-form-autosave.service.ts:47`), хотя ID 31 лежит на leaf `:projectId/edit`. Получается `Number(undefined)`.
- Binding реагирует и на начальную загрузку пустого файла (`ProjectFormService.initializeProjectData`, `patchValue`), и на пользовательское удаление. Неверный запрос не имеет видимого пользователю состояния ошибки; 404 не попадает в очередь сетевых ошибок.
- Общий явный save вызывает `getFormValue → stripNullish`, который исключает пустую строку. Поэтому он не дублирует неудачную очистку и не восстанавливает согласованность ссылки/файла.
- Backend удаляет файл и `UserFile` отдельно от URL в `Project`. Проверенный локальный CDN-транспорт удалял физический файл; реальные авторизация и модели backend не подменялись. Production CDN и его восстановление не проверялись.

## Требования к отдельному исправлению

Передать в cleanup-autosave проверенный ID редактируемого проекта из соответствующего контекста; не подставлять 0/первый ID и не маскировать пропуск сохранения. Отделить инициализацию формы от пользовательской очистки. Сохранять намеренную очистку полей в явном save, не меняя глобальную семантику `stripNullish` для чужих форм без анализа. Обеспечить согласованное удаление ссылки/файла и корректную обратную связь об ошибке; не отключать autosave целиком. Точные изменения порядка операций и компенсации выбрать при реализации и проверить на отказах.

Не ремонтировать чужие данные и не менять React, current_application, права лидера/участника, программные связи, правила подачи или виджет. Реальная браузерная проверка в этой диагностике выполнена для презентации; аналогичный binding обложки виден в коде, но отдельное удаление обложки ещё требуется проверить.

## Приёмка и регрессионные проверки

- Реальная вложенная маршрутизация и DI-scope в тесте: правильный ID для первого/следующего проекта, разные projectId/programLinkId; начальная загрузка пустых файлов не отправляет cleanup PUT. Не ограничиваться mock ActivatedRoute с ID прямо в root.
- Удаление презентации и обложки, явное сохранение пустого значения, API-readback после ухода/повторного открытия; ни одной сохранённой ссылки на удалённый файл и ложного сообщения об успехе.
- Отказы DELETE/PUT, offline/reconnect/очередь, смена проекта, уничтожение компонента и поздние ответы: ошибка видима, изменения не теряются, запрос не уходит к другому проекту.
- Существующие сохранение обычного поля, case связи текущей программы и разрешённая сдача работают; права члена команды не расширены.
- Targeted-тесты причины, полный Angular suite, lint и build на окончательной версии. Известную ngx-autosize teardown ошибку отдельно отразить, не подавлять.
