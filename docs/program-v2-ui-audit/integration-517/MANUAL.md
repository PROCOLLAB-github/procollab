# Ручная интеграционная приемка PR #517

Это проверка кода PR с настоящим dev API до merge. Открытая общая dev-версия приложения не доказывает работу PR. Моки из предыдущего визуального этапа здесь не применяются. Пароли и токены вводятся только в обычной форме приложения в браузере владельца; передавать их в чат или запускать команды с ними не требуется.

## 1. Запустить изолированный код PR

В Linux/macOS/WSL, из существующего Angular checkout, без переключения рабочей ветки:

```sh
git fetch origin refs/pull/517/head:refs/remotes/origin/pr517-acceptance
git worktree add --detach ../procollab-pr517-acceptance origin/pr517-acceptance
cd ../procollab-pr517-acceptance
PR517_EXPECTED_SHA=$(git rev-parse HEAD)
git show --no-patch --format='%H %s'
npm ci
bash docs/program-v2-ui-audit/integration-517/start-preview.sh "$PR517_EXPECTED_SHA"
```

Сверить SHA с вкладкой Commits PR #517. Если каталог worktree уже существует, использовать новый пустой путь; не стирать прежние изменения. Скрипт прекращает запуск при несовпадении SHA, измененных исходниках или неожиданной конфигурации API. Сервер слушает только `127.0.0.1:4317`, production-конфигурация не используется. Sentry в development выключен существующим `sentry.config.ts`. Не нужен reverse proxy, отключение CORS, перенос cookies с dev-сайта или изменение общего dev.

В Cloud точный `0a589f4c` уже проверен таким изолированным запуском: обычная форма входа, реальные GET 200 для V1/V2, GET управления 401 и переход на вход без сессии. После исправления R1 проверять актуальный head PR, а не оставаться на `0a589f4c`. Новый код и проверенные хеши описаны в README этого каталога и итоговом сообщении.

Остановить preview можно Ctrl+C. Изменения данных dev, сделанные через preview, настоящие: локальный frontend не создает копию базы.

Не экспортировать HAR, storageState, cookies, request headers, ответ `/api/token/` или приглашения с секретными ссылками. В матрице достаточно метода, пути без секретных query-параметров, статуса и видимого результата.
3. Открыть локальные ссылки:
   - V1: `http://127.0.0.1:4317/office/program/39/management/settings?tab=basic`.
   - V2: `http://127.0.0.1:4317/office/program/49/management/settings?tab=basic`.

Названия: №39 — `[ТЕСТ] Кейс-чемпионат «Город будущего» — 60 проектов`, №49 — `[QA 26.10] Кейс-чемпионат — решения`, №50 — `[QA 26.10] Хакатон — решения`, №51 — `[QA 26.10] Неконкурсная программа — решения`. 6. Для записей выделить внутри тестовых программ данные с префиксом `PR517-<дата>` и зафиксировать их обычные ID. Нужны: два кейса A/B; две сданные работы одного кейса и еще одна другого; хотя бы один черновик; эксперт E1 для всех кейсов, E2 для A, E3 — участник собственной команды; число оценщиков 2. 7. Если такой набор отсутствует, подготовить его через обычные UI: для V1 тестовые участники создают Project в «Мои проекты» и сдают его в V1; для V2 капитан создает заявку на странице программы и заполняет/сдает самостоятельное Solution. Участников команды добавлять только из существующих тестовых аккаунтов. Не конвертировать Solution в Project, не переключать storage mode и не менять данные других тестировщиков. Если заглушка/тестовый адрес не подтверждены, сценарий приглашения остается NOT TESTED. Напоминания участникам и выдачу сертификатов не запускать.

Сроки №39/49 могут относиться к разным этапам. Перед оцениванием убедиться, что сервер разрешает его сейчас. Настройку этапа менять только в выделенном тестовом наборе, если это не влияет на других пользователей. Запрет из-за календаря — бизнес-ограничение, а не автоматически дефект PR. Если нельзя безопасно подготовить этап, соответствующий сценарий остается NOT TESTED.

Поля программы, критерии, календарь и quota действуют на всю программу. Префикс работ не изолирует эти параметры. Перед такими записями подтвердить, что программа выделена приемке и все ее участники тестовые. Если №39/49 используются параллельно или содержат реальные контакты, ограничиться чтением; глобальные изменения оставить NOT TESTED до получения отдельной тестовой программы через штатные средства администратора. Не делать SQL-копии, миграции или изменение storage mode ради теста.

## 3. Сохранение настроек — отдельно V1 и V2

1. В «Основное» записать исходное описание. Добавить маркер `PR517-<дата>`, сохранить, дождаться успешного ответа и перезагрузить страницу. Маркер должен остаться. Открыть ту же программу в другой вкладке: должно быть серверное значение, а не только состояние первой формы.
2. Так же проверить обратимое поле в «Сроки», тестовый материал, тестовый критерий и поле анкеты регистрации; после каждого сохранения выполнить reload. Существующие критерии/снимки с оценками не удалять и блокировки не обходить.
3. В V1 «Кейсы и поля» изменять только тестовую Project-форму. В V2 проверить форму Solution и ее revision/snapshot: до сдачи изменение разрешается сервером, после сдачи отображается сохраненный snapshot. Старый Project не должен появляться как обязательная сущность V2.
4. «Организаторы»: чтение, поиск, меню и сохранение роли проверить только на дополнительном тестовом организаторе, не удаляя последнего/текущего организатора. Если операция вызывает письмо и тестовый транспорт не подтвержден, не выполнять ее.
5. Вернуть обратимые настройки и повторным чтением подтвердить восстановление. Не удалять поля/критерии, для которых сервер уже запрещает удаление после ответов/оценок. Отдельно отметить неизменяемые тестовые записи.

## 7. Конфликты, ограничения и права

1. Ревизия настроек: открыть редактируемую форму в двух вкладках A/B. В B сохранить новое тестовое значение; в A сохранить старую версию. Для форм с optimistic revision ожидается конфликт 409 без перезаписи B и возможность обновить данные. Не требовать 409 от полей, где контракт использует обычный PATCH без revision; отдельно записать фактическую семантику.
2. Назначения: открыть назначения/preview в A; в B изменить те же тестовые назначения или quota; подтвердить старое в A. Сервер должен отклонить устаревшую revision/план. Перечитать, проверить сохранение валидного локального выбора и отсутствие автоматического повторного apply. Сначала прочитать серверный итог, потом решать, повторять ли действие.
3. Защита оценки: открыть редактор назначения в A, в профиле эксперта B сохранить оценку той же работы, затем в A попытаться снять прежнее неоцененное назначение. Сервер повторно проверяет актуальное состояние и не удаляет сохраненную оценку. Допустим предусмотренный контрактом конфликт/отказ; успешное уничтожение оценки — FAIL.
4. Solution: два капитанских окна одного черновика; B сохраняет/сдает, A пытается сохранить старую expected_version/form revision. Ожидается конфликт без потери B и без автоматического повторения submit. Отдельно проверить устаревшую форму организатора.
5. В профиле обычного участника и эксперта открыть organizer management URL напрямую. Должен быть отказ сервера 403/404 и отсутствие закрытых данных. Анонимный профиль должен перейти на вход, а прямой API GET — 401. Последний сценарий уже выполнен; он не подтверждает проверки авторизованных ролей.
6. Участник одной тестовой команды открывает ссылку другой команды/программы; эксперт пытается открыть неназначенную и собственную работу. Серверные permissions определяют отказ или read-only в зависимости от режима; запись запрещенного результата не происходит. Видимость disabled кнопки сама по себе не доказывает server-side защиту.
7. Не подменять ответы API, версии, роли и permissions через Playwright routes/DevTools overrides, не отключать защиту браузера. Если реальный отказ записи невозможно воспроизвести через штатные действия, пометить прямую server-side запись NOT TESTED, а не считать UI-блокировку достаточным доказательством.
